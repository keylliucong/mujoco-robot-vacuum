## 阻断 2：斜向 +30° 假通过 / 完成跨越的证据

**原问题**：末帧只接触地面、横移 1.2 m、yaw −53.7°，旧判定只看 `advance` 与 `t_recover`，于是 `passed=1`。

**改了什么（含仿真专家返工①②）**

- 新增“跨越证据”：`judge.py:278` 起
  - `crossed_front`：质心投影 `com_progress_m >= step_front_m`（重心越过台阶前缘）；
  - `within_width`：`|end_lateral_m| <= step_half_width_m`（没有绕过台阶端部）；
  - `reached_platform`：窗内最大机体高度 ≥ `step_height_m - platform_height_tol_m`；
  - **`ended_on_platform`（专家①）**：`both_wheels_on_top`（两轮都在台阶上，`all`）**或** `no_floor_contact_at_end ∧ height_ok`（末帧离地且高度够平台）；任一驱动轮在台阶、另一轮还在地面的“骑棱边”不再算完成；

## 阻断 3：时步依赖远超门槛（控制更新率已剥离）

**原问题**：2 ms 通过；1 ms 的 `t_recover` 0.744→4.188 s（5.6×）、接触峰值 +66%；0.5 ms 超时。

**先修实现污染（专家③）**：`scripts/run_cases.py:869-876` 原来每个仿真步调用一次 `set_drive`，缩小时步等于把速度环更新率按 `1/h` 翻倍，`kp/yaw_damping` 的等效增益随步长变。现改为**固定绝对时间周期**更新（`cases/_runner.json:drive.update_period_s=0.002`，即 500 Hz；`next_control += control_period`），步间 `ctrl` 保持；台账新增 `prototype.runner.control_update_period_s`。

**为什么最终用 2 ms 而不是专家建议的 20 ms**：先按建议把 `update_period_s` 设为 `0.02` 实跑 base（其余不变），20 mm 工况不再通过——末帧横移 `2.020 m`、`cross_fail_reasons=[lateral_outside_step_width, not_ended_on_platform]`，说明 50 Hz 控制带宽不足以保持航向。没有为 20 ms 重调 `kp/yaw_damping`（超出本轮范围）。因此采用 2 ms（500 Hz）：它是**固定的绝对周期，不随 h 缩放**（h=2/1/0.5 ms 时分别每 1/2/4 个物理步更新一次），既去掉 1/h 污染，也不改变 base 档已验证的控制器带宽。

**固定控制更新率后的 Windows 三档（`outputs\g2_p_baseline\run.json`）**

| 档 | `timestep_s` | `passed` | `failure_primary` | `t_recover_s` | `advance_m` | 峰值 N（relative-only） | `max_pos_z_m` | `cross_fail_reasons` |
|---|---|---|---|---|---|---|---|---|
| base | 0.002 | 1 | — | 0.744 | 1.136 | 174.78 | 0.01481 | — |
| 1 ms | 0.001 | 0 | `cross_fail` | 5.238 | 0.536 | 223.06 | 0.01012 | lateral/height/ended/gap |
| 0.5 ms | 0.0005 | 0 | `cross_fail` | —（未恢复） | 0.00047 | 220.57 | 0.00030 | front/height/ended |

- 控制更新率固定后，峰值差从原来的 +66% 降到 +27.6%，`t_recover` 从 4.188 s 变为 5.238 s：**控制带宽解释了那部分差异，但没有带来收敛**。1 ms 与 0.5 ms 彼此接近（223/220 N，都爬不上去），2 ms 才是离群点。
- 固定 `h=2 ms` 改 `solref` 的扫描仍成立：`0.01` 峰值 174.8 N、`0.003/0.002` 均 527.1 N、`0.02` 为 122.0 N，结论随刚度翻转（Mac 同提交 `/tmp/exp/*/run.json`；峰值数值不随控制更新率改变）。
- **`solref=0.003` 与 `0.002` 结果相同，是被 `2×timestep=4 ms` 的有效下限截断**：说明 2 ms 这一档的可调接触刚度范围已经压在下限附近，**不是安全点**；0.01 s 只是在这条窄带里被选中的一个点。

**结论（按仿真专家指定措辞）**

> **时步敏感且未收敛；结论只在 `h=2 ms ∧ solref=0.01 s` 这一点成立，禁止跨时步比较与外推；下游不得混入 1/0.5 ms 数据。**

**峰值身份（仿真专家指定）**

- 174.8–290.7 N 是 `solref` 与步长共同决定的**数值峰值，不具物理量含义**；527 N ≈ 18 倍整机重也不能当强度/保险杠输入。
- 允许：同机型、同 `h`、同 `solref` 下比较不同几何/摩擦/限扭配置（相对量）。
- 禁止：跨 `h` / 跨 `solref` 当物理量比较；作强度或保险杠输入；出现“冲击力”表述。
- `run.json.data_quality.peak_contact_force` 已写入上述身份与限制；载荷谱导出必须带 `timestep_study`，未证明收敛时只能标 `relative-only`。

### 5.6 签后必修：`slip_force_exceeded` 浮点容差（`c2dbcf1`）

**原问题**：逐样本复算时，各接触对的 `|Ft|/Fn` 最大值恰好压在摩擦锥面上（floor `0.800000000`，μ=0.8；step `0.600000003`，μ=0.6）。旧写法 `abs(tangent)/normal > mu` 会把 `μ+1e-9` 的浮点噪声判成超限，导致 `slip_force_exceeded` 在 baseline 与斜向 ±30° 全为 `True`，判据恒真。

**新行**（`judge.py:592`）：

```python
if abs(tangent) / normal > mu * (1.0 + 1e-6):  # arithmetic：浮点容差
```

1e-6 相对容差只吸收“力点正压在锥面上”的数值噪声，不改变真实超限的判定。

**负例证据**（`verify_structure.py` 的 `抽查4/6`，合成 `normal=5.0`）：

  ratio= 0.8000016000000001
