## 阻断 1：倾角单位错（弧度当度比 25）

**原问题**：`judge.py` 把 `pitch_rad` 直接和 `tilt_pitch_deg=25` 比较，`pitch_max_deg` 字段里装的其实是弧度，`topple` 永远不触发。

**改了什么**

- 判定前统一换算：`judge.py:259` `pitch_max = math.degrees(_abs_max(pitch, window))`，`roll` 同（`:260`）。字段名 `pitch_max_deg` / `roll_max_deg` 与单位一致（`:418` 附近 metrics）。
- 判据参数键仍是 `tilt_pitch_deg` / `tilt_roll_deg`，含义与单位一致。
- 自检加负例：`scripts/verify_structure.py:994` 起把整段时程 `pitch_rad` 置 `math.radians(50)`，要求 `passed=0`、`failure_primary="topple"`，并断言 `49 <= pitch_max_deg <= 51`（`:1007`）。

## 阻断 2：斜向 +30° 假通过 / 完成跨越的证据

**原问题**：末帧只接触地面、横移 1.2 m、yaw −53.7°，旧判定只看 `advance` 与 `t_recover`，于是 `passed=1`。

**改了什么（含仿真专家返工①②）**

- 新增“跨越证据”：`judge.py:278` 起
  - `crossed_front`：质心投影 `com_progress_m >= step_front_m`（重心越过台阶前缘）；
  - `within_width`：`|end_lateral_m| <= step_half_width_m`（没有绕过台阶端部）；
  - `reached_platform`：窗内最大机体高度 ≥ `step_height_m - platform_height_tol_m`；
  - **`ended_on_platform`（专家①）**：`both_wheels_on_top`（两轮都在台阶上，`all`）**或** `no_floor_contact_at_end ∧ height_ok`（末帧离地且高度够平台）；任一驱动轮在台阶、另一轮还在地面的“骑棱边”不再算完成；
  - `contact_gap_max_s`：首触到重心越过前缘之间，任一机体-台阶接触同时为空的最长空档，门限 `contact_gap_tol_s=0.1 s`。
- **新增 `cross_fail`（专家②）**：`judge.py:352` 不再把未跨越兜进 `bottom_out`；不满足的子条件逐项写入 `metrics.crossing.cross_fail_reasons`（`front_edge_not_passed` / `lateral_outside_step_width` / `platform_height_not_reached` / `not_ended_on_platform` / `step_contact_gap_too_long`）。`bottom_out` 只保留真正的壳体-台阶托底。
- `passed` 必须同时满足 `crossed_ok`：`judge.py:391-395`。
- 参数来源：`scripts/run_cases.py:1006` `build_judge_params` 注入 `step_front_m`、`step_half_width_m`、`heading_rad`、`com_offset_x_m`；门限写入 `cases/_runner.json` 与台账行 `prototype.judge.step_contact_gap_tol_s`。
- 自检负例：`scripts/verify_structure.py:1009` 起构造“末帧回地面、横移 1.2 m、台阶接触中断”的时程，要求 `cross_fail`；`:1067` 起再构造“一轮台阶、一轮地面（骑棱边）”的时程，要求 `ended_on_platform=false` 且 `cross_fail_reasons` 含 `not_ended_on_platform`。

**`bottom_out` / `slip` 是否在 `fail_on`（专家②要求写明）**

- `cross_fail` 与 `bottom_out` 已显式列入所有 step 工况的 `fail_on`；未跨越或真托底都直接失败。
- `slip` 仍是**诊断量**，不单独判失败：它的 μ 门来自【工程假设】，且运动学滑移率在台阶棱边会自然超阈；把它当失败门会把正常爬坡误杀。报告读 `slip` 时只看趋势，不作通过/失败依据。

## 阻断 3：时步依赖远超门槛（控制更新率已剥离）

**原问题**：2 ms 通过；1 ms 的 `t_recover` 0.744→4.188 s（5.6×）、接触峰值 +66%；0.5 ms 超时。

**先修实现污染（专家③）**：`scripts/run_cases.py:869-876` 原来每个仿真步调用一次 `set_drive`，缩小时步等于把速度环更新率按 `1/h` 翻倍，`kp/yaw_damping` 的等效增益随步长变。现改为固定 2 ms 时间周期更新（`cases/_runner.json:drive.update_period_s=0.002`，即 500 Hz，与 base 步长一致），步间 `ctrl` 保持；台账新增 `prototype.runner.control_update_period_s`。

**固定控制更新率后的 Windows 三档（`outputs\g2_p_baseline\run.json`）**

| 档 | `timestep_s` | `passed` | `failure_primary` | `t_recover_s` | `advance_m` | 峰值 N（relative-only） | `max_pos_z_m` | `cross_fail_reasons` |
|---|---|---|---|---|---|---|---|---|
| base | 0.002 | 1 | — | 0.744 | 1.136 | 174.78 | 0.01481 | — |
| 1 ms | 0.001 | 0 | `cross_fail` | 5.238 | 0.536 | 223.06 | 0.01012 | lateral/height/ended/gap |
| 0.5 ms | 0.0005 | 0 | `cross_fail` | —（未恢复） | 0.00047 | 220.57 | 0.00030 | front/height/ended |

- 控制更新率固定后，峰值差从原来的 +66% 降到 +27.6%，`t_recover` 从 4.188 s 变为 5.238 s：**控制带宽解释了那部分差异，但没有带来收敛**。1 ms 与 0.5 ms 彼此接近（223/220 N，都爬不上去），2 ms 才是离群点。
- 固定 `h=2 ms` 改 `solref` 的扫描仍成立：`0.01` 峰值 174.8 N、`0.003/0.002` 均 527.1 N、`0.02` 为 122.0 N，结论随刚度翻转（Mac 同提交 `/tmp/exp/*/run.json`；峰值数值不随控制更新率改变）。
- **`solref=0.003` 与 `0.002` 结果相同，是被 `2×timestep=4 ms` 的有效下限截断**：说明 2 ms 这一档的可调接触刚度范围已经压在下限附近，**不是安全点**；0.01 s 只是在这条窄带里被选中的一个点。

**结论（按仿真专家指定措辞）**

> **时步敏感且未收敛；结论只在 `h=2 ms ∧ solref=0.01 s` 这一点成立，禁止跨时步比较与外推；下游不得混入 1/0.5 ms 数据。**

**峰值身份（仿真专家指定）**

- 174.8–290.7 N 是 `solref` 与步长共同决定的**数值峰值，不具物理量含义**；527 N ≈ 18 倍整机重也不能当强度/保险杠输入。
- 允许：同机型、同 `h`、同 `solref` 下比较不同几何/摩擦/限扭配置（相对量）。
- 禁止：跨 `h` / 跨 `solref` 当物理量比较；作强度或保险杠输入；出现“冲击力”表述。
- `run.json.data_quality.peak_contact_force` 已写入上述身份与限制；载荷谱导出必须带 `timestep_study`，未证明收敛时只能标 `relative-only`。
