## 三、必须改（本轮新发现，1 条）

**M1 · G2.5 的证据表不能从本提交重建。** `docs/验证输出/2026-11-22_原型批次_*` 的 `run.json` 写着 `contract_version=1.7.1`、`git.commit=f428c19`、`command=null`，其 `cases[]` 带 `outcome` / `failure_mode` / `A1–A4` / `v_impact_mps` 等字段；而全仓没有任何 `.py` 产出这些列（`git log --all -S "first_contact_wheel" -- '*.py'` 只命中早期原型提交）。也就是说：**这批表来自一个不在本 PR、也不在 main 的旧管线**，引用它等于引用一份无法重建的证据（S11 的同一条道理）。
落法（二选一，由你排）：① 用当前 `run_cases.py` 重生成这批表（列变成 `status/passed/failure_primary/...`，与契约一致）；② 承认它是历史快照，按 ADR README 第 4 条钉 `frozen_at=` + `ref=`，并声明不参与现行判定裁决。

## 四、建议改（3 条）

- **S1 · 第二入口 `scripts/run_oomwoo.py`。** 它复用 `run_cases` 但注入独立台账，并在内部补了 `model_checks` 的两个洞（`body_length()` 只认 box 机身、`chassis_min_z()` 用包围球近似圆柱）。补丁本身有记录，但**观测口径被分叉到两个入口**：同一个概念在两处算，迟早不一致。建议把两处修进 `model_checks`，wrapper 只保留"换台账路径"这一件事。
- **S2 · `cases/_runner.json` 原本不在契约里。** 本轮已补进 §2（数字的四个家 + 可覆盖须记 `overrides[]`），但代码侧还没实现"case 覆盖 runner 默认"的通道。G3 扫参数时一定会有人想改 `platform_height_tol_m`，先把这个通道做出来，比事后解释便宜。
- **S3 · `failure_primary` 的兜底已修**（命中但未列入 `fail_on` 时不再落 `timeout`），但 `failure_flags` 里仍会出现 `timeout`（`passed=0` 时无条件追加）。建议只在"窗口耗尽仍未恢复"时加，否则 `flags` 里同时出现 `topple;timeout` 会让人以为超时是主因。

## 六、`failure_mode` 的落法（你问的那条）

先纠正一个前提：**它不在代码里**。当前 `run_cases.py` / `judge.py` 不产出 `outcome` / `failure_mode`；这两个词只出现在上面那批不可重建的证据表里。所以不该"把契约同步到它"，而该：

1. **契约只收两个新失败类别**：`belly_contact`、`cross_fail`（它们在 `FAILURE_ENUM`、`FAILURE_PRIORITY` 和三个 case 的 `fail_on` 里，是真实的判据变更）；
2. **`outcome` / `failure_mode` 明确为派生的展示标签**，不进 `summary.csv` / `run.json`，由入库脚本从 `(status, passed, failure_primary, failure_flags)` 生成；
3. 越过五条件写进 §3.1，作为 `passed` 的正式定义。

条文已落 **PR #42 / v1.9.0 / ADR-016**（判据集变更，开版触发①）。合入顺序：与 #39 同批，#39 侧把三处常量改 `1.9.0`，否则 S14 会红。
