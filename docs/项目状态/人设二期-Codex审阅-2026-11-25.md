## Q1｜哪些 P0 应当触发停手

**结论**　P0 应明确暂停哪项动作、留下什么证据、满足什么条件可恢复。全项目停摆仅适用于无法隔离影响的情况。格式、检查方法和发版组织通常属于 P1；错误放行、冻结件被改、独立验证失去资格，以及并发写入破坏基线，应在受影响范围内拦住。

**结论**　建议四人引用文末相同的四条团队 P0。各角色专属 P0 写清自己签什么、遇到什么时停手、证据交给谁。B 的 P3 拆回 P0 授权路由与 P1 代码执行分工；简短、表格、三档意见样式和命令排版归 P2。

## Q4｜远端核不到时怎么写

**结论**　原句会把证据可达性变成交付者需要自行消除的阻塞，可能诱发越权推送、强推或上传受限数据。建议把本地完成声明、远端事实和放行状态各写明。

**理由**　GitHub 不可达、PR 已关闭、HEAD 不符、产物受限所需动作不同。权限内的复核人可先查本地证据或受控位置；远端已可查但声称的 SHA 不存在，需退回更正。已有仓库规则允许 GitHub 不可达时保留本地提交与具体错误。D 提到的 PR #35 已由 GitHub 核实为已合并，说明开始动作前需要重读远端状态。[协作规则](../../AGENTS.md) · [工作流 SOP §5](工作流SOP.md) · [PR #35](https://github.com/keylliucong/mujoco-robot-vacuum/pull/35)

**替换 D「回报五项且远端核不到算未完成」**　「按 SOP 回报五项。提交已在本地检查、远端不可达或证据暂不可访问时，报『本地已验证／发布待核』，附本地 SHA 或产物指纹、核验位置、原因、复核人和时间；若 PR 已关闭、HEAD 不符或提交查无，报『状态待纠正』并保留证据。暂停依赖该远端证据的放行，禁止为对账强推、越权发布或上传受限资料；按原授权恢复同步，或由有权限的核验人确认替代证据。」

## Q6｜每份 SOUL 的目标与取舍
