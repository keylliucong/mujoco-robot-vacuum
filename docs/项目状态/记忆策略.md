# 记忆策略

草案。每条事实保留一个有维护人的出处，使用方引用该出处。

| 位置 | 记什么 | 谁更新 |
| --- | --- | --- |
| bot 的 `MEMORY.md` | 只留怎么工作。记角色边界、如何核对和交接、如何找到本目录与自己的 SOP 篇目 | 各 bot 按本岗位维护 |
| `docs/项目状态/` | 项目事实与生效裁定。D-xx 记决定、依据、影响和翻案触发条件，链接卡片、签字、证据和版本。Gate、里程碑和交付状态分别更新看板与交付物索引 | Program-leader 派落盘并追踪合入，主管签字人负责事实，Codex 按签字记录 |
| 契约、试验与报告等技术出处 | 条文、验收限、量测和技术结论正文保存在各自文件，D-xx 只引用对应条款、冻结 SHA 或结果入口 | 主管岗位按工作流维护 |

## 开工、交接、查冲突

1. 接手先取 GitHub 最新状态，核对 `main` 的 SHA、决策编号和在办卡。读取当前生效的条文时看现行契约，复现某批时读该批冻结引用，不移动老 SHA。
2. 新决定先在卡上保存答复与执行人，再由 Codex 将经确认的决定追加到 `决策记录.md`。记录关联卡、责任人、截止、适用机型与证据，并在相应 PR 合入后把 D-xx 回连到卡。旧决定被替代时保留原文并标新编号。交接只传 D-xx、PR、SHA、当前谁做什么和期限。
3. `MEMORY.md` 与仓库冲突，以仓库中生效记录为准。发现冲突的 bot 移除私有事实副本、保留工作方法或入口链接。仓库内下游索引滞后时，Program-leader 挂卡安排更新。PR 合并状态即时核对 GitHub，Gate 是否通过读签字证据与 D-xx。
4. 当仓库中两个项目裁定互相冲突、失效或缺签，暂停引用受影响的决定，指出两处文件、SHA 与影响，交主管岗位补裁定。聊天答复仍待落盘时，卡片显示「已答复、待生效」。重启后从主卡和仓库重建进度，正在跑的任务需现场核实。

示例：MEMORY 只写「签 G2 前查结构规则和证据 SHA」。诸如「G2 已过」「当前并到哪个 PR」「采用哪个标准条文」都通过看板、D-xx 和证据链接查询。

出处：[项目状态说明](README.md)、[决策记录](决策记录.md)、[工作流 SOP](工作流SOP.md)。
