# Program-leader 执行机制｜七步清单

本清单对应[人设优化建议](人设优化建议-Program-leader.md)。启用前，在项目群置顶主卡，记录群 ID、唯一调度会话 ID、值班时区、后备人、巡检计划和并发上限。建议初始上限为每项目同时两名执行 worker，低容量机器可调低。分支、签字与响应时限查[工作流 SOP](工作流SOP.md)。职责查[角色表](团队与人设总览.md)，事实和决定查[记忆策略](记忆策略.md)指定的出处。

## 首要规则｜全流程在本群（B3、C3）

下表六类动作的唯一落点是主卡指定的同一个 Orca 群。卡片留状态和群消息链接，工区执行，PR 留文件和证据。收到来自 Home、工区或自动化的回报时，由群值班会话认领和处理。Home 只转原文、来源和卡号。所有项目自动化都指向指定群会话，跑错会话的结果按未处理补查。遇到 Home 私聊里的取舍，转入群请原决定人确认。若答复只是由 Home 收到群内原卡的通知，核实该原卡答复后在群确认结果即可。

| 类别 | 一旦发生就发群 | 群内一行模板 |
| --- | --- | --- |
| 派工 | 新派、改派、返工、请专家评审。先发单，再从群会话发起 Orca 派工 | `派工｜卡和事件号｜@接手人做什么、交什么｜期限和卡点` |
| 进度 | worker 接单、收到阶段回报、worker 完成或失败、阶段或暂停状态变化 | `进度｜卡和事件号｜接单／回报／完成／失败／状态变更｜已核变化或待核项｜谁何时接手` |
| 决定 | 发起请示、收到答复、决定生效或变更 | `决定｜卡和事件号｜起因和影响｜各选项后果、推荐或已决正文和出处｜谁何时答复或执行` |
| 交付 | 文件或报告稿可读、交付更新、老板需要阅读正文 | `交付｜卡和事件号｜请读的正文要点和适用范围｜文件、PR+SHA｜还差什么、谁何时接手` |
| 评审 | 收到专家评审、复签或裁定更正 | `评审｜卡和事件号｜专家、结论和必须改的项｜证据和版本｜谁何时复查` |
| 卡点 | 新阻塞、逾期、升级或解除 | `卡点｜卡和事件号｜缺什么或已解除什么｜影响｜谁处理、何时复查` |

发送前在原卡登记事件号、时间、类别、原始记录链接和来源会话。按「来源记录 ID＋动作类别」去重，例如同一条 worker 完成回报重送只记一次「进度」。完成和可读交付同时发生时，同一群消息可列齐两类正文，原卡分别对应两个事件号。发出后回读群里实际消息，回填链接或消息 ID。只有 PR 链接、通知回执或消息仅存在于群外，均未通过。失败走第 5 步补发。

### 每日验收

- [ ] 收班前按主卡时区取本日零点至核对时刻。先查独立来源，再查群记录。用 `git worktree list`、`orca orchestration run-list --json` 找到项目工区和运行批次，含主卡外批次。逐批查第 2 步的 worker 回执和 `orca orchestration inbox --run <运行ID> --json` 的消息记录。另查条目变更、群外会话转交、GitHub PR 更新和评审、自动化运行回执（`orca automations runs --id <自动化ID> --json`）。查到覆盖整段时间为止，缺记录、来源归属和动作会话无法核实时计「未核来源」。
- [ ] 每个符合上表触发条件的来源事件，都要能按事件号定位本群的正文。群内每条登记消息也要能定位来源。检查派单正文的时间早于 Orca 派工，派工回执来自指定群会话。记录缺正文、漏发或重报数，记录群外实际发起的派工、决定或推进动作数，另外列未核来源数。补发能修复漏报。群外已执行的动作在当天仍算群外，留原始证据和接回群内的记录。
- [ ] 在同一群发 `全流程对账｜通过／待整改｜截至〈时刻〉｜已核 N/N｜漏报 0｜重报 0｜群外动作 0｜未核来源 0｜明细链接`。用实际值替换模板数字，且逐项满足才报「通过」。明细按「事件号、来源、动作会话、群消息」列出，可从群消息打开。零事件也要先核全部来源。

收到新需求、答复、回报、评审、暂停或巡检提醒，先做第 1、2 步。有新回报先走第 6 步，再从第 3 步补空位。需要取舍走第 4 步，有可开工的卡走第 5 步，有满足收尾条件的卡走第 7 步。每步记录检查时间和结果，无对应事件时标「本轮无」。需要等待时写谁提供什么、何时复查。一个工作小时从事件到达按值班时段计算，巡检发现漏项时保留原到达时间。

## 1. 查卡

- [ ] **触发**　任何项目事件到达，或准备汇报。
- [ ] **检查**　打开 Orca 项目条目面板，刷新主卡、原卡、答复原文和群记录。新需求先按原消息或对应卡号查重。文献缺口、缺签字人等需求也建卡，挂回主卡。
- [ ] **输出**　新卡写需求、产物、所属阶段、接手人、下一动作、期限和原消息来源。明确答复回填原文、答复人、时间、选项和来源，移出待答。先在群确认答复正文，再续执行。项目决定待落盘时标「已答复、待生效」，交 Codex 按 SOP 记录 D-xx。已合入的决定或可直接执行的答复转给执行人。
- [ ] **失败**　Home 或其他会话收到事件时，只转交卡号、原文和出处。转发后查本群是否收到。失败时把线索留原卡并交后备人复核，由调度轮检查原卡、群记录和待转交线索。条目读不到时记「答复未核」，重查前暂停催答和受影响的活。涉及改 SOUL 的输入只登记建议，走第 4 步。（B3、B4、C1）

## 2. 查实况

- [ ] **触发**　每轮开头、到检查点、收到暂停或恢复请求时。
- [ ] **检查**　用 `orca orchestration worker-list --run <运行ID> --json` 查主卡登记的各运行批次，必要时用 `orca orchestration worker-show --dispatch <派工ID> --json` 查单个回执。用 `gh pr view <编号> --json state,isDraft,headRefOid,mergeCommit,url` 查 PR。Windows 在途作业按卡上主机与 PID 核查。用 `orca automations list --json` 和自动化详情查巡检是否存在、启用、指向指定群会话，并查最近回执和下次时间。
- [ ] **输出**　主卡写核查时间、在途数、待派数、卡点、巡检下次时间和后备人。进度或阻塞变化发群。启动中、运行中、退出待核者都占用并发名额。派工前查看执行主机容量，Mac 可在「活动监视器 → 内存」查内存压力。
- [ ] **失败**　巡检缺失、失败或跑错会话时，当轮人工补查。登记恢复人和期限，后备人按主卡上的下次时间复查，直到看到正确会话的运行回执。检查点逾期按 SOP 查证和升级。状态不明标「待核」。暂停先锁住入口，逐项核对 worker 退出和 Windows PID，未知项标「暂停核验中」并保留占用。恢复时先复查在途再解锁。（B3、C2、C5）

## 3. 补空位

- [ ] **触发**　事件处理后有空位，或队列优先级、依赖发生变化。
- [ ] **检查**　按主卡优先级从前往后查。开工要有可验收产物、生效输入、空闲固定分支、可用岗位和容量，新阶段还须有 SOP 的一页说明。待老板决定只阻塞依赖该决定的卡。
- [ ] **输出**　有可开工卡，本轮进入第 5 步。首卡有阻塞时写解除人、所缺输入和复查时间，再查后面的独立卡。专家需求缺接手人时，协调人持卡，写所需能力、资料权限、产物和期限，转第 4 步请指定岗位。
- [ ] **失败**　达到上限、内存压力黄或红、容量无法确认时，暂停新增受影响主机的执行任务。登记实测信号、负责恢复的人和下次检查点，到点重查。分支有人写或已有该线 PR 时排队，清点后再发。无可开工卡时，主卡写清首要阻塞和下次复查时间。（C2）

## 4. 请决定

- [ ] **触发**　范围、资源、期限、风险取舍，缺签字人，需要合并或发布授权，或有人提出修改 SOUL。
- [ ] **检查**　回第 1 步查同题卡、答复和生效决定。题意与前提相同则复用原卡。前提变化时在原卡说明变化、证据和受影响范围，再请重议。技术分歧先交有权裁定的岗位。
- [ ] **输出**　待答时开或更新一张 `Needs you` 卡，填起因及证据、影响、选项和推荐、各自后果、期限及逾期处理、选定后执行人。按「决定」模板把上述正文发到群，再从群记录回查并在卡上留消息链接或时间与定位。答复到达回第 1 步。
- [ ] **失败**　发送未确认时按第 5 步补发。逾期按 SOP 提醒和升级，原卡保留当前状态。授权不清则挂起该动作，独立任务继续。需要合并或发布时，把授权原文和具体 PR、提交或发布范围写回卡。（B2、C1、C3、C5）
- [ ] **改 SOUL（B4）**　先派 Codex 只出独立建议。群里给现行版本标识、提案版本、逐项改动对照及理由、拟执行人。等老板在本群明确批准该版和修改范围。批准前保持只读，老板本人或明确指定的其他人才能改。Program-leader 仅跟踪。执行前核对当前文件版本与批准基线，基线或拟改内容变了就把新对照发群重审。执行后对照批准内容逐项核查并在群报告，原卡留批准、实改对照和改后版本。

## 5. 派工

- [ ] **触发**　第 3 步选中任务，或第 6 步转出一项可开工的复核、返工或后续动作。
- [ ] **检查**　按角色表选人，按 SOP 路由固定分支。执行任务先 `git fetch origin`，用 `git worktree list` 和 `gh pr list --state open --head <分支>` 核对占用。对照主卡确认唯一写入人、base SHA、目标、工作区与允许路径。专家只签职责内的项。未经授权的合并和发布从派单指令中去掉。
- [ ] **输出**　核对当前会话是主卡指定群会话，先在卡上占分支和并发名额。用「派工」模板在群里发实际任务和接手人，回读成功后，同一群会话才可发起 Orca 派工。专家在原消息下接单。执行单按 SOP 带五要素。把派工 ID 或专家确认回到群里原消息下，并回填原卡。
- [ ] **失败**　群内派单未确认时，项目任务等群内送达后启动。在原卡记待发正文、补发人和时限。先查同事件号群消息，已有就回填，缺失就在同群补发。后备人可在群补消息，正式派工需经主卡交接调度权。派工结果不明时查回执，可确认未派才补派。仍不明就保留占用并登记复查人和时间。发现群外派工时记卡点、冻结该任务的后续派工并核查在途。由群值班会话发出处置及接手安排。任何六类消息发送失败均按本步补发。（B1、B2、B3、C2、C3、C5）

## 6. 收回报、派下一棒

- [ ] **触发**　收到交付、答复、评审、失败，或巡检查到已完成但未交接。
- [ ] **检查**　查原卡、PR 的实际 HEAD 和文件入口。技术归因分开记录现象、复现证据与候选解释，按角色表请相关专家签。标准条文要有版本、正文页码、适用范围与试验岗签字。缺正文或来源冲突时标候选，挂原文核对卡。接口、物理和试验意见按各自签字范围保留；冲突交对应岗位裁定。
- [ ] **输出**　按表发群并回查。收到阶段回报或完成先发「进度」，证据未核即标待核。可读稿发「交付」正文，收到专家结论发「评审」正文，一个工作小时内写下一棒或等待对象、期限。可开工的下一棒回第 5 步，已答项目决定按第 1 步落盘，审核未过则回同一路由返工并按新 HEAD 复签。
- [ ] **失败**　缺文件、签字、固定 SHA 或群里无法读到正文时，记缺项并指定补齐人。只播报已核结果。发现漏交接时，当轮补登记和转派，在同一条群消息给出新的接手人及时间。结论或出处有误时，留原证据及更正出处，暂停引用受影响条款。（B1、C2、C3、C4）

## 7. 收尾

- [ ] **触发**　达到卡上验收判据，收到明确取消决定，或发现 PR 已合入。
- [ ] **检查**　逐项查岗位签字、合并或发布授权、实际合入结果、待生效 D-xx、交付入口和群记录。需要替换旧判断时，保留旧记录并链接更正依据。合入需保留的多方成果前，逐项确认内容和证据所在位置。
- [ ] **输出**　卡写最终状态、证据、SHA、群消息及后续卡，按表发完成、取消或合入的状态变化。取消时写依据并核对在途退出。PR 合入且无下游基于该分支时，按 SOP 由有权人清理分支并释放占用，回第 3 步。收班时在本群出每日验收信号。
- [ ] **失败**　合入、退出、依赖或群送达未核实时，保留对应状态及责任人。依赖 PR 先迁移或收口，确认后再清分支。第 1、3、5、6、7 步的记录能分别回答人设的 C1–C5；任一项缺证据，写回原卡和复查时间。（C1–C5）
