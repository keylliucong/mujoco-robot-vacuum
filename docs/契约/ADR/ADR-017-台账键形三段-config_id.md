# ADR-017：台账键形归架构师，形状定为三段（`machine.config_id.量名`）

- 状态：已采纳（契约 v1.9.1，开版触发①）
- 背景：试验标定作为台账 owner，直接定了 `<machine>.<payload>.<param>` 的键形（`payload ∈ {dry, ballast, full}`），理由是 v1.4 要求两套载荷配置各占一键。它随后自己发现越界：《团队与人设总览》写的是「改 schema 或数据字典的接口定义」归架构师。裁定请求给了 A（键形归架构师，它提需求）与 B（键法属它，形状会签）。
- 选项：① A；② B；③ 三段照它提的 `payload` 段。
- 选择：**A**，并给出形状 **`<machine>.<config_id>.<量名>`**。理由分两层：
  1. **归属**：键形是 schema，schema 归架构师；台账 owner 管的是**取值、来源、量测可用性**（它已做得对，`label`/`status`/`ref` 的填法都是它的活）。这条界线要一次划清，否则以后每个字段形状都要会签。**形状归我，值归它**——这就是 A 的内容，不是 A 与 B 的折中。
  2. **形状**：不能用 `payload` 作第二段，因为 **S21 的分组键是（`payload_state`, `config_id`）**。`payload_state` 只有空载/满载两值，而同一载荷可以有两种实体配置（`sealed_full_water` / `equiv_ballast`）。只放 `payload`，这两套配置的同一个量（满载 `com_x`）**会撞键**；补救办法只能是在量名里再编一次配置——配置写两遍，正是我们要躲的隐式耦合。用 `config_id` 一段同时完成两件事：区分载荷态、区分同载荷的两种实现；而且它已经住在 `ref` 里（28 行在用），进键后与 `ref` 逐字相同、可机检，不产生第二个家。
- 代价：
  - **第二次迁移**：308 行要再改一遍键。**实现侧已迁完**（#44 合入 `own.unloaded.m_dry` 等三段键），本条的作用是把契约追平——在此之前 main 上是"实现三段、条文两段"，S14/S23 处于自相矛盾状态。
  - 键变长；`config_id` 含点会成为解析歧义，所以定成硬约束（含 `.` 即失败）。
- 翻案条件：若将来出现"同一配置下同一量有多个测次/多台样机"（例如 own 有两台整机），`config_id` 不足以区分，那时需要第四段（`sample_id`）或把机型段升级为"机型×样机"。到那一步本条重写。
- 关联：契约 §4 台账键法、S23、抽查 17、ADR-014（其两段式被本条取代）、ADR-005（载荷成套与分组键）。

## 一条可迁移的经验

**键要能表达"它属于哪个不可交换的组合"，而不是"它属于哪个粗分类"。** `payload` 是粗分类（两值），`config_id` 才是那个组合（无界、由 S21 定义）。用粗分类做键，等于让键在一个维度上故意留空——留空的代价迟早由使用方用命名约定补上，而命名约定就是隐式耦合。
