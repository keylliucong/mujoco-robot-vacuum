# ADR-016：受阻要有名字——`belly_contact` / `cross_fail` 与越过五条件

- 状态：已采纳（契约 v1.9.0，开版触发①：现行判据无法给真实受阻一个结论）
- 背景：G2.5 用 oomwoo 跑 12.5 / 20 / 30 mm 三档。20 mm 与 30 mm 上，车头从动轮（r = 12.5 mm）与刚性壳体前下缘先碰到台阶立面，**驱动轮整个判定窗口都没碰到台阶**。旧口径的触发点是"首次驱动轮-台阶接触"，于是 `t_trigger` 不存在 → 判 `invalid:never_contacted` → 不进通过率分母、不属于任何失败类别、也不进 `failure_flags`。
  - 也就是说：**一次确定、可重复、可复现的受阻，在数据里表现为"这次没测到"。**
  - 第二个洞在同一处暴露：旧 `passed` 只看 `advance ≥ 1 个车身长`。机体被顶回时位移可能仍凑够；反过来，真的上了平台但差几毫米也会被判"没过"。位移是结果，不是"越过"这件事本身。
- 选项：① 保持 `invalid:never_contacted`；② 用现有 `bottom_out` 顶替；③ 新增 `belly_contact` / `cross_fail`，并把"越过"写成可观测的五条件。
- 选择：③。
  - **不选 ①**：`invalid` 不进分母，等于把失败洗成缺失，还让通过率虚高。`invalid` 的本义是"这次数据不能用来判"，而这里数据很好，结论也很明确：没过去。
  - **不选 ②**：`bottom_out` 指底盘几何触地或触棱；`belly_contact` 指壳体前下缘顶住立面且驱动轮够不到。两者对应的工程改法不同（抬高离地间隙 vs 减小前悬/加倒角/加抬升），混用一个名字，半年后没人分得清改哪。
  - ③ 的落地：`passed` 改为四条同时成立（越过五条件 / 恢复前进 / 位移 / 无判退项）；五条件（前缘、横向宽度、平台高度、末态在平台、接触空档）的细分原因只进 `run.json.cases[].crossing`，不进 `summary.csv` 列。两个新类别默认只做诊断，是否判退由 case 的 `fail_on` 决定——擦底是否算失败取决于实机口径，那是验收限的事，不是契约的事。
- **为什么不把 `outcome` / `failure_mode` 写进契约**：它们是 `(status, passed, failure_primary, failure_flags)` 的别名。项目已经为"同一个事实两套名字"付过一次代价（pair 摩擦 3 分量当 5 分量用，见 ADR-015）。报告层叫 `cleared` / `blocked`、叫 `lift_fail` 都可以，但必须由入库脚本从存储字段派生，手填的表格在复核时重建不出来（同 S11）。所以契约只写一条：派生标签不入存储。
- 代价：枚举 10 → 12；judge 多两个 flag 与一棵 crossing 子树；`_runner.json` 里多两个容差（`platform_height_tol_m`、`step_contact_gap_tol_s`），因此 §2 补记了"数字的四个家"，避免容差藏在第二个文件里不被发现。每新增一种受阻机理，都必须回答"它是新类别，还是现有类别的参数"。
- 翻案条件：出现越过五条件之外的越障形态（例如多级台阶需要逐级计数），把 `crossing` 从布尔升级为分级事件序列，本节重写。
- 关联：契约 §3 / §3.1 / §2、S25、抽查 19、ADR-015（同一事实两套名字的代价）。

## 可迁移的两条

1. **"数据无效"永远比"判失败"好写，所以它是把失败洗成缺失的快捷方式。** 判据里每留一个 `invalid` 出口，都要问一句：这是真没测到，还是没过去？前者是流程问题，后者是结论。
2. **同一个事实不要有两套名字。** 报告可以换词，存储只能留一套；多出来的那套词汇不会有自己的测试，只会在某次合并里悄悄漂移。
