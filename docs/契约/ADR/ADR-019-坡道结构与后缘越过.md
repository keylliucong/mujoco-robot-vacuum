# ADR-019：坡道是另一类越障；「越过」要用后缘量

- 状态：已采纳（契约 v1.11.0，开版触发①：R3 冻结前发现现行条文给不出坡道结论、且"越过"有两套口径）
- 背景：R3 要把"六条判退"冻结成可执行定义，撞上两处结构缺口。
  - **坡道无处安放**：`scenario` 只有 `obstacle`（台阶），`kind` 只有 `flat|step`。于是"跌落""仍在起始侧""整体越过"只能标 `N/A`——**`N/A` 不是"未通过"，是"这条判据对这次运行不适用"**；把本该判退的工况写成 `N/A`，等于用空白充当结论。
  - **越过有两套量**：现行 `crossed_front` 用质心越过前缘，而"整机越过"的物理含义是**后缘**离开台阶前缘。两量差约 0.2 m；不统一，同一批数据会同时存在"质心过了算过、后缘还在外面"的两种说法，而报告上看不出用的是哪一套。
- 选项：① 把坡道塞进 `obstacle`（加 `shape: "ramp"`）；② 新增 `kind: ramp` + 独立 `ramp` 块；③ 越过保持质心，另加一列 `s_rear` 供参考；④ 越过换后缘，质心降为诊断。
- 选择：② + ④。
  - **不选 ①**：坡道没有前缘、棱边这些字段，塞进去会让 `obstacle` 一半字段对一半场景无意义，并且必然出现"台阶与坡道同时配一半"的非法状态。**场景类型是 `kind` 的职责**，不是几何字段的取值。
  - **不选 ③**：加一列而不改判定，等于把"两套越过"合法化，谁来引用都会挑对自己有利的那套。旧量可以留，但只能留作**诊断**。
  - ④ 的落地：`crossed_front ⇔ s_rear ≥ step_front_m`，`s_rear = s − L_rear`，`L_rear = x_rear_B·cos(pitch)`（`x_rear_B` 从模型 `chassis_*` 几何取、进台账，不写死 0.20）。`com_progress_m` 保留进 `run.json.cases[].crossing`。
- 坡道判退三条（跌落 / 仍在起始侧 / 未登顶整体越过）的**阈值归仿真专家**，落 `_runner.json` + 台账；契约只定结构与输出落点。失败类别**不新增**：跌落算 `topple`、未登顶算 `cross_fail`、失速算 `stall`——失败类别说"怎么没过去"，不说"路是什么形状"。
- 顺带修的旧账：`invalid_reason` 表里原本混着两种东西——运行期原因（进 `summary`）与配置拒绝码（fail-fast、根本不产 `summary`）。`step_too_narrow_for_heading` 属于后者，却躺在运行期表里。v1.11.0 拆成两张表，并新增 `ramp_angle_out_of_range`。**"没跑"和"跑了但无效"必须分家**，否则通过率的分母永远说不清。
- 代价：`kind` 三值 + 一个新块；judge 多一条坡道分支；已合的 G2/G3 台阶批次**必须按后缘量重判**，结论可能翻转（旧量比新量激进 0.2 m），历史表要并列两个判据版本。坡高派生（`length·sin(angle)`）意味着改坡长会改坡高——这是有意的，避免"坡长 1.2 m、坡高 0.3 m"这类自相矛盾的工况。
- 翻案条件：若出现"变坡度 / 弧形坡"，`angle_deg` 单值不够，需升级为分段几何；届时本节重写，`kind` 仍是 `ramp`。
- 关联：契约 §2、§3、§3.1、§3.2、S27、抽查 21、ADR-016（失败类别命名）、ADR-018（判据粒度）。

## 可迁移的两条

1. **`N/A` 不是结论。** 判据表里每一个 `N/A` 都在提示"这条判据缺输入或场景缺结构"；缺结构就补结构，别让它长期占着"不适用"的位置——它看起来像已经审过了。
2. **同一件事只能有一个判定量。** 允许两个量并存，就一定有人引用对自己有利的那个；旧量可以保留，但必须明确降级为诊断，且写明它不再参与判定。
