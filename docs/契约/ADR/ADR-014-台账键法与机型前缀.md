# ADR-014：台账键法——`machine` 前缀进键，一表一套唯一性

- 状态：已采纳（契约 v1.8.1，开版触发①：实现期证明现行条文不可实现）
- 背景：`docs/参数溯源.csv` 在 PR #24 合入后同时承载两批数据，键法不同、零重叠，且各自都有缺陷。
  - main（77 行）：裸语义键（`m_dry`、`com_x`、`Ixx`…），机型靠 `ref` 里的 `machine=own|oomwoo` 区分。**21 个 `param_id` 在两机型间重名**，同一张表里同一个键指向两个不同的物理量。
  - G2 一线（110 行，`machine=prototype`）：路径式键（`mass.chassis`、`judge.window_s`），每行指向模型/配置里的真实位置。
  - 后果一：`docs/不确定度预算.csv` 按 `param_id` 与台账联表（S19）。键不唯一，联表就会把 oomwoo 的预算串到 own 的参数上——**校验失效时不报错，只给出一个看起来合理的结论**。
  - 后果二：main 的 `xpath` 列被占位字符串填满（`TODO(试验标定)` 40 行、`N/A(基准机型，未入 MJCF)` 37 行）。v1.7.6 定的是「结论等级只取**绑了 `xpath`** 的行」，而按字符串判断，这 77 行全都"绑上了"——一份没进模型的行会进入等级推导，恰好是 v1.7.6 想避免的事。
  - 后果三：5 个分支（#15/#17/#21/#27/#28）各自携带整份台账，每合一次就撞一次同一文件，冲突内容与本次改动无关。
- 选项：① 裸语义键 + `ref` 带 machine（main 现状）；② 路径式键（G2 现状）；③ 两者分表；④ `machine` 前缀进键 + `xpath` 空表示未绑定。
- 选择：④。
  - **不选 ①**：机型号不是行的注解，是身份的一部分——"同一个量在不同机型上是两个数"。把身份放进自由文本 `ref`，任何按 `param_id` 联表的检查都会跨机型串行，而 `ref` 是人读的，写错不会有任何东西失败。
  - **不选 ②**：路径式键只对"已经进了模型"的行成立。main 那 77 行没有模型可指（oomwoo 无几何数据、own 待测），硬套路径只能编一个，编出来的路径就是第二个占位符。
  - **不选 ③**：分表会让"一个数两个家"重新开缝——计划行与模型行同名不同表，升格时谁删谁是人工纪律；且 S10 的 XML↔台账比对要跨两个文件。**空 `xpath` 已经足够表达"未绑定"**，不需要第二张表。
  - ④ 的细则：
    1. `param_id = <machine>.<量名>`；`machine ∈ {own, prototype, oomwoo}`，新增机型先改契约取值表，不许临时起名。
    2. 量名的形状由**该行有没有真实 `xpath` 指针**决定：有 → 路径式（`prototype.mass.chassis`、`prototype.judge.window_s`）；无 → 语义式（`own.m_dry`、`oomwoo.r_wheel`）。判断依据只有一处（看 `xpath` 列），不是哪一种好看。
    3. 全表 `param_id` 唯一。同一量在另一机型上必须另起一行、另起键。
    4. `xpath` 值域只有两种：空，或指向真实位置的指针。`TODO(...)`、`N/A(...)`、`—` 一律改为**空**。
    5. 未绑 `xpath` 的行照旧不参与等级推导（v1.7.6 已定），**不改任何判据**。
  - 迁移：一次性脚本（加前缀 → 占位清空 → 唯一性断言）单独 PR 进 main，预算表 43 行的 `param_id` 同步加 `own.` 前缀；**先合这条，再让 5 个分支 rebase**。顺序反了，每次 rebase 都会各自再造一遍同样的冲突。
- 代价：键变长；`run.json.params`、预算表、报告表头都要带 `machine` 前缀；两种键形状共存，读表先看 `xpath` 列。全部可由一条脚本兜住（S23）。
- 翻案条件：若出现"同一机型多台物理样机需要各自实测"，`machine` 要从机型细化为样机实例（`own-01`、`own-02`）；届时扩取值表即可，规则本身不变。
- 关联：契约 §4、S23、抽查 17、ADR-012（参数行等级只从 `label` 读）。

## 可迁移的两条

1. **一列里可以共存两类行，但"没有"必须用空值表达，不能用占位字符串。** `TODO(...)` 让所有"有没有绑上"的检查恒真——检查通过，判据却判在一行不存在的数据上。这比缺规则更难查：日志全是绿的。
2. **合并冲突的根因常常不是文本冲突，而是键里少了一个维度。** 21 个重名不是"命名不统一"，是"身份不唯一"；补上缺失的维度后，冲突从结构上消失，而不是靠谁记得按顺序解。
